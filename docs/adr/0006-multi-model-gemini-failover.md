# Multi-Model Gemini Failover on the Free Tier

This project runs on a free Google AI Studio account, where every model has small, independent rate limits (per-minute RPM, per-day RPD, per-minute-tokens TPM) that were cut 50–80% in December 2025 — e.g. Gemini 2.5 Pro is ~5 RPM / 50 RPD, 2.5 Flash ~10 RPM / 250 RPD, while Gemma sits at ~30 RPM / 14400 RPD. A single hard-coded model therefore stops serving requests well before the user's actual need is met. To keep the app working without a billing account, `GeminiService` (the single chokepoint every AI feature already calls) transparently fails over across a ranked set of free models so a user's request is fulfilled even when individual models are capped.

**Ranked, capability-tagged roster, quality-first.** Models are tried best-first and degrade gracefully: `2.5-pro → 2.5-flash → 2.0-flash → 2.5-flash-lite → 2.0-flash-lite → gemma-4`. Endurance-first ordering (high-quota models first) was rejected because it would serve every request from a weaker model even when better quota is available; the cascade naturally slides down to high-endurance models (Gemma, validated to support `responseSchema` + JSON mode) only under load. Each model carries capability flags (`vision`, `schema`); a call is only routed to models that support what it needs — Equipment Analysis requires vision + structured output, Progression/Program require text + structured output. `gemini-3.x` models are excluded: they are paid-tier preview only.

**Self-healing roster.** A `404` (deprecated/renamed model — exactly the failure that retired `text-embedding-004` and broke startup) or a model a free key may not call causes a *permanent* skip for the process lifetime plus a loud log. The curated list can therefore go stale without taking the app down; it corrects itself and tells us via logs. This is why the roster is a plain hard-coded constant rather than env-driven config.

**Stateful cooldown, driven by the real error envelope.** A `429 RESOURCE_EXHAUSTED` response carries `error.details[]` with a `google.rpc.QuotaFailure` (which quota broke) and a `google.rpc.RetryInfo.retryDelay`. We keep an in-memory `Map<model, availableAt>` (NestJS singleton — survives across requests, resets on restart) and set the cooldown from `retryDelay`: an RPM breach frees the model in ~60s, an RPD breach parks it until midnight Pacific. Transient failures (`503` overloaded, `500`, and `fetch` timeout/throw — `fetch` has no default timeout, so an `AbortController` bounds it) are treated as failures too: the model gets a short (~10s) cooldown and we switch immediately rather than retrying the same model, since the deep fallback bench makes same-model retry a pure latency cost. State is in-memory, not Postgres/Redis — adequate for a single free-tier instance.

**Terminal behavior: bounded wait, else fail fast.** When every eligible model is cooling down at once, if the soonest one frees within a small bound (~5–8s, i.e. an RPM blip) we wait and retry once; otherwise (RPD-level, hours away) we throw a typed `AllModelsExhausted` error carrying the earliest retry time, which the controller surfaces as `503 + Retry-After`. Always-waiting was rejected because an all-RPD exhaustion would hang a request until midnight.

**Embedding is the exception — seed-time failover only.** `embed()` powers coaching-knowledge retrieval (pgvector cosine search). The corpus is embedded once at seed time; queries are embedded at suggestion time and compared against it. Because different embedding models produce *different vector spaces*, embedding a query with a fallback model while the corpus sits in the primary model's space yields plausible-but-meaningless cosine results — silent corruption, strictly worse than the existing graceful degradation (`progression.service` already wraps retrieval in try/catch and proceeds with no coaching context on failure). Therefore failover for `embed()` applies **only at seed time**: walk the embedding roster (`gemini-embedding-001 → gemini-embedding-2`, all pinned to `outputDimensionality: 768` to match the `vector(768)` column), record the winning model in a nullable `coaching_knowledge.embedding_model` column, and *always* embed queries with that recorded model. If the recorded model is capped at query time, we skip coaching context rather than query a mismatched space. Full per-row failover with corpus re-seeding was rejected as too heavy for a hobby app.

This extends ADR 0003 (Gemini for Equipment Analysis) and ADR 0005 (Gemini for Progression Suggestions): the provider and structured-output pattern are unchanged; only the model-selection layer inside `GeminiService` becomes a resilient cascade.
